# db-config — v0.10.2 Auto-Migrate Schema Spec

**Date:** 2026-05-19
**Status:** Shipped

## Goal

Close a real DX gap: consumers should not have to construct a `DbConfigDbContext`
manually and call `Database.MigrateAsync` before `AddDbConfig`. Auto-apply the schema by
default, matching Hangfire / Marten / Wolverine conventions. Provide a clean opt-out
(`SchemaMode.None`) and a `DbConfigMigrator` static helper for DBA-controlled or CI/CD
schema management.

Patch release — additive only.

## Scope Classification

- **Type:** moderate / additive feature + ergonomic fix
- **Implementation path:** subagent
- **Security impact:** low — auto-migrate runs as the configured connection user; if
  that user lacks DDL permissions, the call fails fast at startup (preferable to silent
  schema drift)
- **Breaking-change risk:** behaviour change only — `AddDbConfig` now applies pending
  migrations by default. Hosts that already migrated manually see a no-op (EF Core's
  `__EFMigrationsHistory` tracks state). Greenfield pre-1.0, so this is acceptable.

## Out of Scope (v0.10.2)

- Customizable migration timing (always synchronous before first `Load()`) — async
  pre-build orchestration was considered and rejected as overengineering for the v0.10.x
  series
- Schema name customization beyond the existing default (still `dbo` on SQL Server, `public`
  on PostgreSQL)
- Automatic rollback / down migrations — EF Core migrations are forward-only by design
- Multi-instance migration coordination beyond what EF Core already provides (transaction
  + advisory lock) — documented startup race caveat

## Public Contract Changes

### `SchemaMode` enum (new, in `Moberg.DbConfig.Core`)

```csharp
namespace DbConfig.Core;

public enum SchemaMode
{
    /// <summary>Auto-apply pending migrations at host startup. Default.</summary>
    CreateIfMissing,

    /// <summary>Skip migration entirely. Host assumes the schema is already correct.</summary>
    None,
}
```

### `DbConfigOptions.SchemaMode` (new property)

```csharp
public SchemaMode SchemaMode { get; set; } = SchemaMode.CreateIfMissing;
```

### `DbConfigMigrator` static helper (new, in `Moberg.DbConfig.EntityFrameworkCore`)

```csharp
public static class DbConfigMigrator
{
    public static Task MigrateAsync(
        DbContextOptions<DbConfigDbContext> options,
        CancellationToken ct = default);

    public static string GenerateCreateScript(
        DbContextOptions<DbConfigDbContext> options);

    public static string GenerateMigrationScript(
        DbContextOptions<DbConfigDbContext> options,
        string? fromMigration = null,
        string? toMigration = null,
        bool idempotent = true);
}
```

- **`MigrateAsync`** — programmatic apply. Same as `ctx.Database.MigrateAsync()` but
  consumers don't construct the context.
- **`GenerateCreateScript`** — full DDL for a fresh database.
- **`GenerateMigrationScript`** — incremental upgrade SQL. `idempotent: true` (default)
  generates SQL that checks `__EFMigrationsHistory` before each step.

### `SqlServerDbConfigOptions` + `PostgreSqlDbConfigOptions` (new, in provider packages)

```csharp
// SQL Server
public static class SqlServerDbConfigOptions
{
    public static DbContextOptions<DbConfigDbContext> ForSqlServer(string connectionString);
}

// PostgreSQL
public static class PostgreSqlDbConfigOptions
{
    public static DbContextOptions<DbConfigDbContext> ForPostgreSql(string connectionString);
}
```

Hide the `MigrationsAssembly("DbConfig.Provider.SqlServer")` magic string from consumer
code. Used as the input to `DbConfigMigrator` helpers.

### UTC value converters (internal, defense-in-depth)

`ConfigEntryEntity.ModifiedUtc` and `ConfigAuditEntryEntity.ModifiedUtc` get
`ValueConverter` registrations so SQL Server's `datetime2` columns are read back as UTC
`DateTime` regardless of how the engine stored them. PostgreSQL `timestamptz` already
handles this; the converter is a no-op there. No schema change.

## Mechanism

`HostApplicationBuilderExtensions.AddDbConfig` constructs an internal `DbConfigBuilder`,
applies the lambda, then before constructing the polling store:

```csharp
if (options.SchemaMode == SchemaMode.CreateIfMissing)
{
    using var ctx = new DbConfigDbContext(efContextOptions);
    ctx.Database.Migrate(); // synchronous; runs before Load()
}
```

The call is idempotent — `__EFMigrationsHistory` records applied migrations.

For `SchemaMode.None`, the call is skipped. The first `Load()` will throw if the schema
isn't actually present (table-not-found from EF Core); the host fails fast.

## Public Surface Code Samples

```csharp
// Default — auto-migrate on startup
builder.AddDbConfig(b =>
{
    b.Options.AppName = "MyApp";
    b.UseSqlServer(connectionString);
});

// DBA-controlled — skip auto-migrate
builder.AddDbConfig(b =>
{
    b.Options.AppName = "MyApp";
    b.Options.SchemaMode = SchemaMode.None;
    b.UseSqlServer(connectionString);
});

// CI/CD pre-deploy job
var opts = SqlServerDbConfigOptions.ForSqlServer(connStr);
await DbConfigMigrator.MigrateAsync(opts);

// Offline SQL generation
var opts = SqlServerDbConfigOptions.ForSqlServer(connStr);
var upgradeSql = DbConfigMigrator.GenerateMigrationScript(opts, idempotent: true);
File.WriteAllText("dbconfig-upgrade.sql", upgradeSql);
```

## Caveats Documented in `operations/migrations.md`

- **Multi-instance cold start:** all instances trying to apply migrations simultaneously
  serialize via EF Core's migration lock. Late joiners see a no-op after ~1 s wait.
- **DDL permissions:** auto-migrate requires `CREATE TABLE` / `ALTER TABLE`. Production
  users without DDL switch to `SchemaMode.None`.
- **No rollback:** EF Core migrations are forward-only. Down-migration requires
  hand-written SQL.

## Test Coverage

- 248 Unit + 82 SqlServer + 77 PostgreSql + 11 E2E = 418 green at ship (up from 407).
- New tests:
  - `SchemaMode.CreateIfMissing` applies migrations on first `AddDbConfig`
  - `SchemaMode.None` skips the call and yields a clear "table not found" error if
    schema absent
  - `DbConfigMigrator.MigrateAsync` is idempotent across both engines
  - `GenerateCreateScript` produces DDL that contains all current tables and indexes
  - `GenerateMigrationScript(idempotent: true)` produces SQL with
    `__EFMigrationsHistory` guards
  - UTC value converters round-trip a non-UTC `DateTime` correctly on SQL Server

## Migration Impact

- **v0.10.1 consumers who already migrated manually:** see a no-op on startup. No code
  change needed.
- **v0.10.1 consumers who DIDN'T migrate manually:** auto-migrate now picks up. If the
  connection user lacks DDL, the host fails fast at startup with a clear EF Core error
  — preferable to the previous silent failure mode (table not found on first store
  query).
- **Sample (`samples/PaymentsApi`):** lost ~10 lines of `ApplyMigrationsAsync` helper.
  Cleaner.

## Shelved

The full **v0.11.0 time-bounded configuration overrides** spec
(`docs/specs/2026-05-19-v0.11.0-time-bounded-overrides.md`) was captured during this
release and marked `Status: Shelved`. The two-table design (defaults + scheduled
overrides) is preserved for future reconsideration. Concerns: uncertain whether the
feature fits db-config's positioning vs cron+PUT, feature-flag SaaS, or proper secrets
managers.

## Assumptions and Risks

| # | Item | Mitigation |
|---|---|---|
| A1 | Auto-migrate is a behaviour change; some teams have policy against startup DDL | `SchemaMode.None` is the documented opt-out; documented prominently in `installation.md` and `operations/migrations.md` |
| A2 | Multi-instance simultaneous startups can serialize on the migration lock for ~1 s | Documented in `operations/migrations.md`; recommend pre-deploy migration step for prod |
| A3 | `GenerateCreateScript` includes migration history table init; running on a database that already has DbConfig schema will fail | Use `GenerateMigrationScript(idempotent: true)` for upgrades; document the distinction |
| A4 | UTC value converter could mask a real bug where consumer stored a non-UTC instant | Defense-in-depth; the converter only normalizes `Kind` to `Utc`, not the underlying value |
