# db-config — v0.10.0 Built-In Auth + Unified Mount Spec

**Date:** 2026-05-18
**Status:** Shipped

## Goal

Relax the "host owns all auth" rule from §0.3 by providing an opt-in built-in cookie
login plus a single-call `MapDbConfigAdmin` mount that gates UI + HTTP API with one
cookie. Drop the path-based list endpoint in favour of a flat `GET /` so the admin UI
can paint immediately without operator input.

## Scope Classification

- **Type:** substantial / API surface / minor version bump
- **Implementation path:** subagent
- **Security impact:** **medium** — cookie auth and a credential validator surface enter
  the package boundary. The validator is consumer-implemented (the package never
  inspects the password); the cookie is signed via ASP.NET Data Protection.
- **Breaking-change risk:** YES — `GET /{appName}/{environment}` (path-based list) is
  removed with no back-compat shim. Greenfield (pre-1.0), so we break cleanly.

## Out of Scope (v0.10.0)

- MFA, rate limiting, or account lockout on the built-in form — single-factor only.
  Internet-facing admin surfaces should compose with a hardened pipeline (pattern 3 in
  `auth.md`).
- Built-in user store — the validator is the consumer's responsibility.
- OAuth / OIDC flows — those are pattern 3 (host pipeline composition).
- Tenant-aware HTTP authorization filter — host composes via existing policies.

## Public Contract Changes

### `IDbConfigCredentialValidator` (new, in `Moberg.DbConfig.Http`)

```csharp
namespace DbConfig.Http;

public interface IDbConfigCredentialValidator
{
    /// <summary>Validates the (username, password) tuple. Return the authenticated
    /// principal on success or null on failure.</summary>
    Task<ClaimsPrincipal?> ValidateAsync(string username, string password, CancellationToken ct);
}
```

Registration is `services.AddScoped<IDbConfigCredentialValidator, MyValidator>()`. The
validator may inject DbContext, hashers, IUserStore, etc.

### `IDbConfigAuthorizationFilter` (new, in `Moberg.DbConfig.Http`)

```csharp
public interface IDbConfigAuthorizationFilter
{
    Task<bool> IsAuthorizedAsync(HttpContext ctx);
}
```

A single-method filter for non-form auth (header tokens, IP allowlists, custom JWT
cookies). Composes with the built-in cookie via `DbConfigUiOptions.Authorization` set
inside `UseBuiltInLogin<T>()` or assigned directly.

The package ships `LocalRequestsOnlyAuthorizationFilter` as a ready-made example
(loopback only; convenient for dev).

### `DbConfigUiOptions` (extended)

```csharp
public sealed class DbConfigUiOptions
{
    public IDbConfigAuthorizationFilter? Authorization { get; set; }
    public string? UnauthorizedRedirectUrl { get; set; }
    public string CookieName { get; set; } = "dbconfig-auth";
    public TimeSpan CookieExpireTimeSpan { get; set; } = TimeSpan.FromDays(7);
    public string? CookiePath { get; set; }

    public DbConfigUiOptions UseBuiltInLogin<TValidator>()
        where TValidator : class, IDbConfigCredentialValidator;
}
```

`UseBuiltInLogin<T>` wires three endpoints (`GET /login`, `POST /login`, `POST /logout`)
on the UI route group and assigns an auto-wired cookie filter to `Authorization`.

### `MapDbConfigAdmin` (new extension, in `Moberg.DbConfig.Ui`)

```csharp
public static DbConfigAdminEndpoints MapDbConfigAdmin(
    this IEndpointRouteBuilder endpoints,
    string prefix = "/admin/dbconfig",
    Action<DbConfigUiOptions>? configure = null);

public sealed record DbConfigAdminEndpoints(RouteGroupBuilder Ui, RouteGroupBuilder Api);
```

Single-call mount: UI at `prefix`, HTTP API at `{prefix}/api`, both gated by the same
cookie. Returns both groups so consumers can chain per-surface customizations.

### `MapDbConfigHttp(prefix, configure)` (new overload)

```csharp
public static RouteGroupBuilder MapDbConfigHttp(
    this IEndpointRouteBuilder endpoints,
    string prefix,
    Action<DbConfigHttpOptions>? configure);

public sealed class DbConfigHttpOptions
{
    public string? ScopeFilter { get; set; }
    public IDbConfigAuthorizationFilter? Authorization { get; set; }
}
```

Used internally by `MapDbConfigAdmin` to share the cookie filter with the HTTP route
group. Consumers in split-prefix deployments can capture the auto-wired filter from
`DbConfigUiOptions.Authorization` and pass it explicitly.

### `GET /` flat entries endpoint (new)

Replaces the path-based `GET /{appName}/{environment}` list. Filters:
`?appName=&environment=&tenantId=&keyPrefix=&take=`. Returns entries ordered
`(AppName, Environment, TenantId, Key)` ASC. Empty array on no match (never 404).
Default `take=1000`, max `10000`.

### Removed: `GET /{appName}/{environment}` (path-based list)

Hard-removed in v0.10.0 with no back-compat shim. The UI loads all entries via the flat
endpoint on first paint and narrows client-side via the toolbar filters.

## Mechanism

`UseBuiltInLogin<T>` registers the validator type on the route group's services (via
the `DbConfigUiOptions` callback) and assigns a `CookieAuthFilter` to
`options.Authorization`. The cookie filter reads `Cookie["dbconfig-auth"]`, unprotects
via `IDataProtectionProvider`, parses the payload (`dbconfig|<username>|<utc-iso>`), and
checks expiry. Unauthorized browser requests get 302 to `/login?returnUrl=...`; API
callers get 401.

`MapDbConfigAdmin` calls `MapDbConfigUi` and `MapDbConfigHttp` internally with the same
options bag, setting `CookiePath = prefix` so the cookie covers both surfaces.

## Public Surface Code Samples

```csharp
// Validator
public sealed class MyValidator(IPasswordHasher hasher, AppDbContext db) : IDbConfigCredentialValidator
{
    public async Task<ClaimsPrincipal?> ValidateAsync(string username, string password, CancellationToken ct)
    {
        var user = await db.Users.FirstOrDefaultAsync(x => x.Username == username, ct);
        if (user is null || !hasher.Verify(password, user.PasswordHash))
        {
            return null;
        }

        var identity = new ClaimsIdentity(
            [new Claim(ClaimTypes.Name, username)],
            "DbConfigCookie");

        return new ClaimsPrincipal(identity);
    }
}

// Registration
builder.Services.AddScoped<IDbConfigCredentialValidator, MyValidator>();

app.MapDbConfigAdmin("/admin/dbconfig", opts =>
    opts.UseBuiltInLogin<MyValidator>());
```

## `returnUrl` Safety

The package rejects:
- Protocol-relative URLs (`//evil.example/...`)
- CRLF injection (`%0d%0a...`)
- Any URL that doesn't start with `/`

Invalid values fall back to the configured prefix.

## Assumptions and Risks

| # | Item | Mitigation |
|---|---|---|
| A1 | Single-factor cookie auth is insufficient for internet-facing surfaces | Document this loudly in `auth.md`; recommend pattern 3 (host pipeline composition) for hardened deployments |
| A2 | Default Data Protection key ring is ephemeral; cookies invalidate on every restart | Same as v0.5.0 encryption — document `PersistKeysToFileSystem` + cert in `auth.md` |
| A3 | Validator is scoped, called inside the request pipeline; long DB lookups in the validator slow login | Out of scope to enforce; document that validators should be cheap |
| A4 | Removing the path-based list endpoint breaks consumers who scripted against it | Greenfield pre-1.0; document in BREAKING CHANGES; the flat endpoint is more capable |
| R1 | A buggy custom `IDbConfigAuthorizationFilter` could allow-all by accident | Default is no filter (open access) so consumer must affirmatively opt in; document filter responsibilities |

## Migration Impact

- **Consumers using v0.9.0 split mount + `RequireAuthorization`:** no code changes
  required. Both `MapDbConfigUi` and `MapDbConfigHttp` still return `RouteGroupBuilder`
  and accept `.RequireAuthorization(...)`.
- **Consumers using v0.9.0 path-based list:** must switch to `GET /?appName=&environment=`.
  The response shape is identical; only the URL changed.
- **No existing consumers on production:** greenfield pre-1.0, no breaking-change window.
