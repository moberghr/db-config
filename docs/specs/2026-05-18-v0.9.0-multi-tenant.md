# db-config — v0.9.0 Per-Request Multi-Tenant Spec

**Date:** 2026-05-18
**Status:** Shipped (B52–B63)

## Goal

One host serves N tenants. Consumer implements `ITenantResolver` to define how tenant identity is resolved (header, JWT claim, route, subdomain — their choice). Standard ASP.NET Core `IOptionsSnapshot<T>` automatically becomes tenant-aware via the underlying tenant-aware `IConfiguration` provider. No custom options API required.

## Scope Classification

- **Type:** substantial / new feature / multi-batch
- **Implementation path:** subagent
- **Security impact:** **medium** — multi-tenant data isolation is a real security concern. The gate is `ITenantResolver`; the resolver is called on every `IConfiguration[key]` read. A buggy resolver returning the wrong tenant id is the primary security risk.
- **Breaking-change risk:** YES — `ConfigEntry` gains a `TenantId` field; schema migration adds a `TenantId` column. Greenfield (pre-1.0) so we can break.

## Out of Scope (v0.9.0)

- Built-in middleware (host owns tenant resolution via the resolver implementation — too many sources to be one-size-fits-all)
- `tenantFilter` on `MapDbConfigHttp` (no automatic per-tenant HTTP auth — host composes via existing policy story)
- Async resolvers (`Resolve()` is sync; complex tenant lookups must pre-cache the resolved tenant id at middleware time)
- Lazy per-tenant loading (we load ALL tenants into memory; documented memory ceiling at ~10K tenants × 100 keys; lazy-load is v0.10.0+ if needed)
- Cross-tenant copy/move workflows in the UI
- Tenant-aware audit retention (audit rows have TenantId column; consumer's cleanup SQL splits by tenant if needed)

## Public Contract Changes

### `ITenantResolver` (new, in `DbConfig.Core`)

```csharp
namespace DbConfig.Core;

/// <summary>
/// Consumer-implemented resolver that returns the current tenant id for the
/// caller's context. Returning null (or empty string) means "no tenant context";
/// the configuration system falls back to global default entries.
/// </summary>
public interface ITenantResolver
{
    /// <summary>Returns the current tenant id or null if no tenant is in context.</summary>
    string? Resolve();
}
```

Registration: `b.AddTenantResolver<TResolver>()` inside the `AddDbConfig` options lambda. If not registered, `NullTenantResolver.Instance` is used (returns null — global-only mode).

### `DbConfigBuilder.AddTenantResolver<TResolver>()` (new)

```csharp
public DbConfigBuilder AddTenantResolver<TResolver>()
    where TResolver : class, ITenantResolver
{
    Services.AddSingleton<ITenantResolver, TResolver>();
    return this;
}
```

Registers the resolver as a singleton in host DI. The resolver can take constructor dependencies (e.g. `IHttpContextAccessor`). Resolved lazily from host DI on the first `TryGet` call after host build.

### `DbConfigConfigurationProvider.TryGet` — now tenant-aware (internal change)

`TryGet` consults the resolver on every call. Resolution order:

1. Call `ITenantResolver.Resolve()`. If null or empty, skip to step 3.
2. If tenant id is non-empty, look up the tenant-specific entry in the in-memory `_tenantData` dictionary. If found, return it (decrypted if secret).
3. Fall back to the global (`TenantId = ""`) entry in the base `Data` dictionary. If found, return it.
4. Return false if neither exists.

This makes `IConfiguration[key]` reads tenant-aware. `IOptionsSnapshot<T>` is scoped per-request and rebinds from `IConfiguration` on each scope — so each request gets its tenant's effective values automatically. No custom options API is needed.

### DB schema: `TenantId` column (unchanged from original plan)

```csharp
public sealed record ConfigEntry(
    string AppName,
    string Environment,
    string TenantId,   // NEW — "" for global default
    string Key,
    string? Value,
    bool IsSecret,
    DateTimeOffset ModifiedUtc,
    string? ModifiedBy);
```

### HTTP API: `?tenantId=` for admin paths (unchanged from original plan)

All existing endpoints accept `?tenantId=` query string parameter (defaults to `""` — global default). The write endpoints accept `tenantId` in the request body.

### UI: Tenant column + ScopeSelector input (unchanged from original plan)

`scopeStore.tenantId`; ScopeSelector gained Tenant input; EntriesTable and EntriesTreeView show a Tenant column with Default/tenant-name badges; CreateEntryDialog pre-fills TenantId from current scope.

## Mechanism

`IConfiguration[key]` calls `DbConfigConfigurationProvider.TryGet`. `TryGet` resolves the singleton `ITenantResolver` from host DI (cached after first call), calls `Resolve()`, and uses the result to select the right entry from the in-memory `_tenantData` dictionary (with global fallback).

`IOptionsSnapshot<T>` is scoped to the DI scope (one per HTTP request). Its factory runs `IConfiguration.Bind(section, options)` once per scope — which drives `TryGet` calls — so each request's scope binds against whatever tenant the resolver returns at that moment.

**`IOptions<T>` caveat:** `IOptions<T>` is singleton-cached. The factory runs once at first access, which typically happens at app startup with no HTTP request context. The resolver returns null. The cached `T` has global values. All subsequent requests reading `IOptions<T>` get that global `T` regardless of tenant. **For any tenant-aware type, consumers MUST use `IOptionsSnapshot<T>`.** Document this constraint loudly.

## Public Surface Code Samples

### Consumer's resolver (reads JWT claim)

```csharp
public class MyTenantResolver(IHttpContextAccessor http) : ITenantResolver
{
    public string? Resolve()
        => http.HttpContext?.User.FindFirst("tenant_id")?.Value;
}
```

### Registration

```csharp
builder.Services.AddHttpContextAccessor();

builder.AddDbConfig(b =>
{
    b.Options.AppName = "PaymentService";
    b.Options.Environment = builder.Environment.EnvironmentName;
    b.UseSqlServer(connectionString);
    b.AddTenantResolver<MyTenantResolver>();
});
```

### Standard options registration (no custom API)

```csharp
builder.Services.Configure<StripeOptions>(builder.Configuration.GetSection("Stripe"));
```

### Consumer service using IOptionsSnapshot

```csharp
public class PaymentService(IOptionsSnapshot<StripeOptions> opts)
{
    public void Charge()
    {
        var stripe = opts.Value; // current tenant automatically — resolved via TryGet
    }
}
```

### The IOptions<T> gotcha

```csharp
// WRONG — IOptions<T> is singleton; cached at startup with null resolver → global values always
public class BrokenService(IOptions<StripeOptions> opts)
{
    public void Charge()
    {
        var stripe = opts.Value; // always global — tenant-specific values never returned
    }
}

// CORRECT — IOptionsSnapshot<T> is scoped; factory runs per request → tenant-specific values
public class CorrectService(IOptionsSnapshot<StripeOptions> opts)
{
    public void Charge()
    {
        var stripe = opts.Value; // tenant-specific (or global fallback)
    }
}
```

## Assumptions and Risks

| # | Item | Mitigation |
|---|---|---|
| A1 | `IOptions<T>` singleton-cached gets stale global data; consumer must use `IOptionsSnapshot<T>` for tenant-aware types | Document prominently in multi-tenant.md, CLAUDE.md §0.8, and architecture.md §2.15 |
| A2 | Resolver is called on every `IConfiguration[key]` read; must be cheap (no I/O, no DB lookups) | Document constraint in multi-tenant.md Limitations; resolver implementations that need I/O must pre-cache tenant id in middleware and read from a cheap store (e.g. `IHttpContextAccessor`) |
| A3 | Tenant data IS in `IConfiguration` reads now (we dropped the defense-in-depth boundary of the old design); a buggy resolver returning the wrong tenant id is the security risk | The resolver is consumer-written and consumer-tested; document that casing is significant and resolvers must be deterministic |
| A4 | Memory holds all tenants × all keys; OK up to ~10K × 100 entries (~200 MB) | Documented scaling limit; lazy-load tracked for v0.10.0+ |
| R1 | Schema migration on big audit tables locks rows | Documented runbook (similar to v0.5.0 collation migration); recommend off-hours apply |
| R2 | Existing consumers see a new TenantId field on ConfigEntry; binding from JSON / DTOs could fail | Greenfield — no published NuGet — but tests must verify backward compat with default-empty values |
