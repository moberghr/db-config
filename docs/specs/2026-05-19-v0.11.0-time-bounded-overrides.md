# db-config — v0.11.0 Time-Bounded Configuration Overrides (Shelved)

**Date:** 2026-05-19
**Status:** **Shelved** — design captured but not pursued. Reconsider when a concrete use case emerges that isn't better served by cron+PUT, a feature-flag SaaS (LaunchDarkly, Unleash), or a secrets manager (Vault, AWS Secrets Manager, Azure Key Vault).

## What was being considered

Add native support for time-bounded config values: `(key, value, validFromUtc, validToUtc)` so admins can schedule a flag flip, define a promotion window, or coordinate a key rotation that takes effect at a specific instant without manual intervention.

## Use cases the feature would have covered

- **Scheduled feature flip** — `Features:NewCheckout = true` starting 2026-06-01 at 09:00 UTC
- **Promotion window** — `Promo:DiscountPct = 20` between 2026-12-20 and 2026-12-26, otherwise the default
- **Coordinated key rotation** — new Stripe key valid from a future instant, old key expires at the same instant
- **Maintenance mode** — enabled between two timestamps with no human intervention
- **Compliance** — "this rule was in effect from X to Y" — audit log already captures who changed what when, but the value's temporal validity itself is data, not just history

## Why it was shelved

1. **Scope creep risk.** db-config's positioning is "database-backed `IConfiguration` provider with a nice editor UI and hot reload." Time-bounded scheduling pushes toward "lightweight feature-flag service" — a real product category with mature competitors.
2. **Most consumers don't need it.** Typical config flips happen "when the deploy ships," not at a future instant. Teams with real scheduling needs already have alternatives (CI/CD pipelines, cron jobs, feature-flag SaaS).
3. **Significant complexity.** Estimated 6 batches, ~2500-3500 lines across schema, store, provider, HTTP, UI, docs.

## Design (preserved for future reference)

### Architectural choice: parent + overrides (two tables)

Single-table approach (drop existing UNIQUE, allow multiple windowed rows per natural key) was rejected because it forced a measurable cost on consumers who don't use the feature (storage, weaker DB-level invariants, slight query overhead).

The preferred design is **two tables**:

```
DbConfig_Entries (existing — unchanged):
  PK: (Scope, Environment, TenantId, Key)
  Value, IsSecret, ModifiedUtc, ModifiedBy

DbConfig_EntryOverrides (new):
  Id Guid PK
  Scope, Environment, TenantId, Key  -- logical FK to parent
  ValidFromUtc DateTimeOffset NULL
  ValidToUtc DateTimeOffset NULL
  Value, IsSecret, ModifiedUtc, ModifiedBy
  Index: (Scope, Env, TenantId, Key, ValidFromUtc, ValidToUtc)
  CHECK: ValidFromUtc IS NOT NULL OR ValidToUtc IS NOT NULL  -- at least one bound
```

### Mental model: defaults + scheduled overrides

- `Entries` row = the "always-valid default" value (current v0.10.x semantics)
- `Overrides` rows = scheduled exceptions to the default within specific time windows
- Resolution at `TryGet("key", now)`:
  1. Find override whose window covers `now` for that key → return it
  2. Otherwise → return entry value → same as v0.10.x

### Overlap policy

- **Write path**: API rejects new override that overlaps an existing override window for same `(App, Env, Tenant, Key)` with 409 Conflict
- **Read path**: deterministic tiebreaker if direct-DB writes produce overlap — pick the row with latest `ModifiedUtc`

### Polling provider behavior

- Loads `Entries` (defaults) as today
- Additionally loads `Overrides` where `ValidToUtc IS NULL OR ValidToUtc > now` (active + future only — never historical-expired)
- For non-users (no overrides), the second query returns empty → zero extra work
- `TryGet` checks overrides first, falls back to entry
- Poll-tick: re-load overrides if any window boundary crossed since last tick (fires `OnReload` for `IOptionsMonitor` subscribers)

### HTTP API

Existing endpoints (`GET/PUT/DELETE /{app}/{env}/{*key}`) — operate on `Entries`, identical to v0.10.x. **Non-users see zero API change.**

New endpoints:
- `GET /{app}/{env}/{*key}/overrides` — list overrides for a key (all of them: past, current, future, with optional filters)
- `POST /{app}/{env}/{*key}/overrides` — create a scheduled override
- `PUT /{app}/{env}/{*key}/overrides/{id}` — extend / edit an override (the "Continue" and "Edit valid-to" flows)
- `DELETE /{app}/{env}/{*key}/overrides/{id}` — cancel a scheduled override
- `POST /{app}/{env}/{*key}/schedule` — **atomic split endpoint**: truncate any active override (or split the entry's default) at `effectiveAt` + insert new override with the supplied value. One transaction.

Query param `?asOf=2026-06-01T00:00:00Z` on existing read endpoints — checks overrides for that timestamp, falls back to entry.

### Atomic schedule endpoint

```
POST /api/dbconfig/api/{app}/{env}/{*key}/schedule
Content-Type: application/json
{
  "effectiveAt": "2026-06-01T09:00:00Z",
  "value": "true",
  "isSecret": false,
  "tenantId": "Acme"
}
```

Server in a single `SaveChangesAsync`:
1. Look up currently-active override or entry default for the key
2. If an override covers `effectiveAt - epsilon`, set its `ValidTo = effectiveAt`
3. Insert new override with `ValidFrom = effectiveAt`, supplied `Value`, `ValidTo = null`
4. Both writes commit atomically

Edge cases:
- `effectiveAt` in the past → 422 Unprocessable Entity ("cannot schedule in the past; use PUT to overwrite the default immediately")
- `effectiveAt` falls inside an existing future override window → 409 Conflict
- Two overrides matching the lookup → 409 Conflict ("ambiguous active override at effectiveAt") — only possible via direct-DB write that bypassed write-side validation

### UI

- Entries grid renders identically for keys with no overrides
- Keys with overrides get a clock icon next to the value
- Click clock (or row expand) → sub-table of overrides with Continue/Edit/Cancel buttons
- Edit dialog gains an "Apply now / Schedule at" toggle
- "Continue" button on rows with `ValidTo` pre-fills New Override dialog with `ValidFrom = previous.ValidTo`, value copied from previous

### Tenant interaction

Resolution order with tenant `T = Acme` and `now`:
1. Tenant Acme override active at `now` → return
2. Tenant Acme entry default → return
3. Global override active at `now` → return
4. Global entry default → return
5. Not found

Tenant axis dominates scope axis only when tenant has an *active* row at `now`.

### UTC handling

All DateTimeOffset values normalized to UTC via EF Core `ValueConverter` registered in `DbConfigDbContext.OnModelCreating`. SQL Server column type: `datetimeoffset(7)`. Postgres: `timestamp with time zone`. Both compare as instants.

This UTC normalization is being shipped independently of this feature — see the separate commit landing the `UtcDateTimeOffsetConverter`. The converter applies to existing `ModifiedUtc` properties first; when this feature is unblocked, the same converter would apply to `ValidFromUtc` and `ValidToUtc` automatically via the same `OnModelCreating` registration.

### Audit log

`DbConfig_AuditEntries` table extends with optional `OverrideId Guid?` column to capture override mutations. The Insert/Update/Delete `Action` values apply equally to default-entry mutations and override mutations; the column tells you which table the row applied to.

## Six-batch implementation plan (preserved)

- **B1**: Schema — add `DbConfig_EntryOverrides` table + `ConfigOverrideEntity` + `ConfigOverride` record. EF model registration including UTC value converter on all `DateTimeOffset` properties. Migrations for both SQL Server and PostgreSQL.
- **B2**: Store layer — `IConfigStore` gains `QueryOverridesAsync`, `GetActiveOverrideAsync`, `ScheduleChangeAsync` (atomic split). Both EfCore and InMemory impls + tests.
- **B3**: Polling provider — in-memory override timeline, boundary-driven `OnReload`, `TimeProvider` integration, transitions latency tests.
- **B4**: HTTP API — overrides CRUD endpoints, `?asOf=`, overlap-validation 409, atomic schedule endpoint, full test coverage.
- **B5**: UI — clock icon on rows with overrides, expand-row to show timeline, Apply-now/Schedule toggle in Edit, Continue button, demo seed with scheduled flag flip + key rotation example.
- **B6**: Docs — new `website/docs/configuration/time-bounded-overrides.md`, architecture `§2.17` entry, README section, sample README update.

## Estimated cost

- ~2500-3500 lines across all batches
- ~15-25 new tests
- Migration risk: **low** (additive — new table, no existing-row changes)
- For non-users: **zero observable cost** (parent table unchanged; override table never queried unless overrides exist)

## Why this might still be worth doing later

If a real customer reports needing scheduled flips or key rotation:
- The design above is solid; pick it up from here
- Cost is bounded and predictable
- Two-table design preserves backward compatibility cleanly
- Architecture maps to user mental model (defaults + overrides)

If no such use case appears within ~6 months of v0.10.x, this design stays shelved indefinitely and the feature is "won't fix — use cron+PUT or a feature-flag SaaS."
