## Critical Rules (Always Apply)

These are the highest-impact rules. Full detailed standards live in `.claude/rules/`.

- **§0.1 — YOU MUST NEVER push to remote without explicit approval**, even with green CI. The engineer reviews the diff first.
- **§0.2 — IMPORTANT: NEVER block on the configuration provider's first load.** ASP.NET Core builds configuration synchronously at host construction, so the store MUST tolerate transient unavailability with a clear `InvalidOperationException` (connection details redacted) rather than hanging or silently returning empty values.
- **§0.3 — NEVER let the React UI reach the database directly.** All UI traffic goes through `Moberg.DbConfig.Http`'s JSON endpoints, even in the sample host. The store abstraction is server-only.
- **§0.4 — NEVER write to a scope outside your `scopeFilter` from the same host.** Writes to other scopes return 403. Use a separately-deployed admin host, or a separate route group gated by a distinct `PlatformAdmin` policy — never both groups under one auth policy, which defeats the separation.
- **§0.5 — NEVER refactor mutation audit writes to fire-and-forget.** Every Upsert/Delete writes its audit row (`AuditEntries` / `audit_entries`) in the SAME `SaveChangesAsync` as the mutation; losing audit rows breaks compliance posture. (Read audits are fire-and-forget by design — that exception is documented in `architecture.md` §2.14.)

Encryption, authorization composition, and multi-tenant resolution live in `architecture.md`
§2.8, §2.12, §2.15 and `project-specific.md` §8.2, §8.14 — not restated here.

## Definition of Done

A change is done when all four hold: (1) `dotnet build src/DbConfig.slnx` clean, zero warnings;
(2) tests green on BOTH SQL Server and PostgreSQL for every new behavior (`testing.md` §4.2);
(3) tests run by invoking the test executable directly, not `dotnet test`, which can report success
on zero tests; (4) `website/docs` updated on public API or behavior changes, and the PR title
describes the user-visible change.
